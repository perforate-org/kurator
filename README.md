# Kurator

独立運営者による P2P マルチモデルデータベース(作業中)。

現在は Phase 4(シャード分割)。

- Phase 0: 単一ノードの Memory-first Storage(KV)、独自の追記型 WAL
  (group commit、fsync、破損末尾の検出と切り詰め)、Snapshot + WAL 再生による
  クラッシュ復旧。
- Phase 1: OpenRaft による単一シャード 3 ノード複製(fsync 後にだけ数える
  quorum commit、リーダー選出、ログ追従、スナップショット転送)と、署名付き WAL
  (各レコードが直前レコードのダイジェストと Ed25519 署名を持つハッシュチェーン)。
  決定論的シミュレーションで遅延・消失・分断・クラッシュ・再起動を注入して検証する。
- Phase 2: 実ネットワーク。QUIC の永続接続でRaft RPC・ログ複製・スナップショット転送を
  独自バイナリ符号化で流し、TLS 1.3 の Raw Public Key(Ed25519)で相互認証する。
  メンバー変更は learner として追いつかせてから voter に昇格し、ノード除去もできる。
  QUIC とシミュレーションは同じ `kurator_raft::Transport` 境界で差し替わる。
- Phase 3: MVCC と単一シャードの直列化可能なトランザクション。各コマンドは版
  (単一ノードでは LSN、レプリカでは Raft エントリの index)で適用され、各キーは
  保持期間(既定 4096 版)ぶんの履歴を持つ。トランザクションは 1 つの版を読み、
  読んだキーと走査した範囲を記録し、書き込みを 1 つのログエントリとして提出する。
  エントリを適用する時点で「読んだ版より後に、読んだものへの書き込みがあったか」を
  検査して commit か abort を決める(楽観的並行性制御)。検査は適用側で行うので、
  どのレプリカもどの復旧も同じ判断になる。
- Phase 4(進行中): キー範囲によるシャード分割(multi-Raft)。シャードはキー範囲
  `[start, end)` とエポックを持ち、それぞれが独立した Raft グループになる。分割は
  ログエントリとして合意され、適用時に状態を分割キーで切り分け、右半分を新シャードの
  最初のスナップショット(シード)として永続化する。新シャードは同じメンバーで選挙を
  始め、版(Raft index)は分割点から続く。分割を逃したノードは新シャード宛ての
  メッセージを受けて空のレプリカを開き、リーダーからスナップショットを受け取る。
  範囲外のキーへのコマンドは適用時に `Misrouted` で現在のシャード記述子を返し、
  クライアントはそれで経路を引き直す。
  メタシャード `s0`(TiKV の PD、ICP のレジストリに相当)はクラスタ創設時に同じ
  投票者で作られる分割されない Raft グループで、新シャードの ID 割り当て(トランザクション
  で `next` を進めるので再利用されない)と、全シャードの配置(範囲・エポック・レプリカ・
  メンバー変更のログ位置)の登録簿を持つ。配置の報告は(エポック, メンバー変更位置)が
  新しいときだけ記録されるので、遅延・重複・順不同で届いてよい。クライアントは登録簿が
  キー空間を隙間なく覆うとき、その地図で経路を引く。レプリカの移動は学習者として追加 →
  追いついたら昇格 → 移動元を外す、の順。
  シャード横断トランザクションは Percolator 型の二相コミット。クライアント(調整役)は
  各シャードをそのリーダーが適用した版で読み、シャードごとに下書きを持つ。commit では
  まず各シャードに `Prepare` を送る。シャードは適用時に読んだものを検査し(Phase 3 と
  同じ楽観的検査)、他の準備中トランザクションのロックとぶつからなければ書き込みを
  保留して、読んだキー・書くキー・走査した範囲をロックする。次に最初に書くキーの
  シャード(プライマリ)へ `Decide` を送り、そこでの決定が commit 点になる。他の
  シャードにはその後で伝える。各シャードは決定を記録するので、同じ決定を何度
  伝えてもよく、遅れて届いた `Prepare` は何もロックしない。調整役が途中で倒れて
  残ったロックは、プライマリに問い合わせ(決まっていなければそこで abort して)
  解決する。準備中のトランザクションがあるシャードは分割を拒む。
  調整役は各 `Prepare` に期限(調整役どうしが共有する時計のミリ秒)を書き、ロックは
  それを持つ。期限を過ぎたロックに出会った書き込み・トランザクション(と settle)は、
  そのトランザクションをプライマリで解決してから進む。シャードは期限を保持して返す
  だけで、適用時に時計を読まないので、どのレプリカも同じ判断になる。時計のずれは
  解決が早すぎる(abort になる)か遅すぎる(ロックが長引く)だけで、結果はプライマリが
  決める。
  メタシャードへの呼び出し(ID 割り当て・配置の報告・登録簿の読み出し)はどのノードからでも
  できる。ノードはメタシャードのリーダーへ QUIC で呼び出しを送り、相手がリーダーでなければ
  返ってきたリーダーの手がかりを辿る。各ノードは 2 秒ごとに、自分が率いるシャードの配置を
  報告する。
  決定記録は二段階で回収する。まず全シャードに柵(期限の地平)を立てる。柵を立てた
  シャードは、期限が柵より前のトランザクションの準備と、知らない決定を以後すべて拒む。
  柵より前のロックが残っていれば、プライマリで解決してから柵を立てる。全シャードに
  柵が立った後で、期限が柵より前の決定記録を各シャードが消す。こうすると、消した
  記録を問い合わせに来る者も、遅れて届いた準備が鍵をロックし直すこともない。

| crate | 役割 |
| --- | --- |
| `crates/codec` | 共通のバイナリ符号化(`Reader`、ファイル枠 `Format`) |
| `crates/crypto` | 署名鍵と署名。どれもアルゴリズム(`Algorithm`、今は Ed25519)の識別子を持ち、耐量子暗号(ML-DSA など)へ用途ごとに移せる。`NodeSecret` から用途(`KeyPurpose`)ごとの鍵を導出 |
| `crates/wal` | 追記型 WAL。チェックサム版と署名版 |
| `crates/storage` | 版付きの状態、トランザクション(二相コミットの準備と決定を含む)、キー範囲 `Span`、group commit、スナップショット、`Db` |
| `crates/shard` | シャード記述子(ID・範囲・エポック)、分割、`ShardMap`、シャードの状態 |
| `crates/consensus` | 合意層の境界: `Replicated`・`Transaction`(上位層が見るレプリカ)、`NodeId`・`Peer`・`Role`・`Members`。今は Raft が実装し、将来は BFT に差し替える |
| `crates/meta` | メタシャード: シャード ID の割り当て、配置の登録簿 `Registry`、配置の報告。合意層には `Replicated` 越しにだけ触れる |
| `crates/client` | クライアント: 通信形式(`Request`・`Call`・`Reply`)とノード側の `answer`、シャード地図とリーダー追従で経路を決める `Client`、シャード横断トランザクションの調整役 `Coordinator` と決定の回収 `Collector`(`Shards` 越しに動くので sim も同じコードを使う) |
| `crates/bft` | BFT 合意の試作: 2 段階確定の HotStuff(ビューごとにリーダー交代、タイムアウト証明)を、時計も I/O も持たない決定論的な状態機械 `Core` として実装。投票は安全性の状態(`Safety`)を永続化してからでないと送れない。悪意あるノード(沈黙・二重提案・二重投票・なりすまし)を含むシミュレーションで検査。まだ `Replicated` には繋がっていない |
| `crates/raft` | Raft ログストア・状態機械・スナップショット・`Replica`、シャードごとのレプリカを束ねる `Store` |
| `crates/sim` | 決定論的シミュレーション(シード付きネットワークと障害、参加・離脱、分割、レプリカ移動。シャード横断トランザクションは `kurator-client` の調整役で動かす) |
| `crates/net` | QUIC トランスポート(quinn、Raw Public Key の相互認証。署名方式は鍵のアルゴリズムに従う。鍵交換は耐量子のハイブリッド X25519MLKEM768 のみ、暗号は aws-lc-rs) |
| `crates/node` | `kurator` バイナリ: ノード 1 つ(全シャードのレプリカ)をプロセスとして動かすコンソール |

シミュレーションは既定で 12 シード。`KURATOR_SIM_SEEDS=500 cargo test -p kurator-sim --release`
で増やし、失敗したシードは `KURATOR_SIM_SEED=<seed>` で再現する。

## ローカルで 3 ノードを動かす

各ノードはディレクトリに秘密 `node.secret` を持ち、そこから WAL 署名鍵と通信鍵を
用途別に導出する。`kurator key` は秘密を作り(既にあれば読み)、通信鍵の公開鍵を表示する。

```sh
cargo build -p kurator-node
K=target/debug/kurator
K1=$($K key n1); K2=$($K key n2); K3=$($K key n3)
P1=1=127.0.0.1:7001,$K1; P2=2=127.0.0.1:7002,$K2; P3=3=127.0.0.1:7003,$K3

# 端末をノードごとに分けて起動する。--found を付けた 1 台がクラスタを作る。
$K run --id 1 --dir n1 --listen 127.0.0.1:7001 --peer $P2 --peer $P3 --found
$K run --id 2 --dir n2 --listen 127.0.0.1:7002 --peer $P1 --peer $P3
$K run --id 3 --dir n3 --listen 127.0.0.1:7003 --peer $P1 --peer $P2
```

起動したノードは標準入力からコマンドを読む。書き込みと読み出しはキーを持つシャードの
リーダーで行う(`status` でシャードごとのリーダーが分かる)。メンバー変更はノードが持つ
全シャード(メタシャード `s0` を含む)に適用される。

```text
put <key> <value> | del <key> | get <key> | split <key> | shards
status | members | add <id> <addr> <key> | promote <id> | remove <id> | collect | quit
```

`split m` は `m` を含むシャードを `m` で分け、`m` 以降を新シャードにする。新シャードの
ID はメタシャードが割り当て、分割後の両半分を登録簿に報告する。`shards` はこのノードが
率いるシャードの配置を報告してから、登録簿にある全シャードの範囲・エポック・レプリカを
表示する。どちらもメタシャードのレプリカを持つノードならどこからでも実行でき、呼び出しは
メタシャードのリーダーに届く。

4 台目を足すには、既存ノードを `--peer` に並べて `--found` なしで起動し、リーダーで
`add 4 127.0.0.1:7004 <4 の公開鍵>` を実行する。スナップショットとログで追いついた後に
`promote 4` が通る(追いつく前は `cannot vote yet` で断られる)。`remove <id>` で抜く。
再起動は同じコマンドを `--found` なしで実行すればよい。

クライアントもノードと同じく鍵で認証する。ノードには信頼するクライアントの公開鍵を
`--client <key>` で渡す(複数可)。クライアントが使えるのはクライアント用の経路だけで、
Raft やメタシャードの呼び出しは断られる。

```sh
C=$($K key client)   # クライアントの鍵。各ノードを --client $C 付きで起動する
$K client --dir client --peer $P1 put apple red put melon green
$K client --dir client --peer $P1 get apple get melon
```

`kurator client` は並べた操作(`get <key>`・`put <key> <value>`・`del <key>`)を
1 つのトランザクションとして実行する。シャードをまたぐときは二相コミットになる。
`--peer` のノードからシャード地図を受け取り、各シャードのリーダーへ直接送る。
`committed at <版>` なら書き込みは確定、`aborted` は競合なので再実行すればよい。

シャード横断トランザクションの決定は、期限から 10 分経つとメタシャードのリーダーが
1 分ごとに回収して忘れる。コンソールの `collect` で今すぐ回収もできる。
