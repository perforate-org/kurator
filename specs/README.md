# 仕様と形式検証(Quint)

プロトコルの設計を [Quint](https://quint-lang.org/) で書き、モデル検査で性質を確かめる。
Rust の Kani 証明(`#[cfg(kani)]`)がコード片の全域性と往復を証明するのに対し、ここでは
複数のレプリカと故障を持つプロトコル全体を、メッセージの遅延・順不同・消失・重複と
クラッシュ込みで調べる。

| 仕様 | 対象 |
| --- | --- |
| `txn/txn.qnt` | シャード横断トランザクションの二相コミット(`crates/storage` の `Prepare`・`Decide`・`KvState::confirm`、`crates/client` の調整役と `Lock::resolve`) |
| `bft/bft.qnt` | `crates/bft` の合意(`HotStuff-2` / Jolteon 型の二連鎖コミット、ビューごとのリーダー、タイムアウト証明によるビュー切り替え、クラッシュからの復旧、委員会の変更によるエポックの終わり) |

## `txn/txn.qnt`

### txn: モデル

- シャードは 1 つの複製された状態として扱い、コマンドはログ順に即座に適用する。
  複製・リーダー・レプリカのクラッシュは合意の仕様の側の話。
- トランザクションが読むキーと書くキーは最初から決まっている。値はそれを書いた
  トランザクションの名前なので、読んだ値から書き手が分かる。
- 調整役はどのステップの後でも止まってよく、止まったまま戻らなくてもよい。誰でも
  いつでもプライマリの決定を他のシャードに伝えてよく、ロックを解決してよい。時計は
  ないので、期限はいつでも過ぎているものとして扱う(早すぎる解決はアボートにしかならない)。
- コミット点はゴースト変数 `serial` に記録する。コミット点の順にトランザクションの
  書き込みを当てた各キーの値で、トランザクションの読みはコミット点でこれと一致しなければ
  ならない。
- 1 シャードで読むだけのトランザクション(`Local`)はログに書かず、`confirm`
  (`KvState::confirm`)でコミットする。

### txn: 保証すること(`safety`、不変条件)

- `serializable`: コミットしたトランザクションは、すべてのシャードで、コミット点の順に
  並べた直列実行と同じ値を読んだ。
- `atomic`: あるシャードがコミットしたトランザクションを、別のシャードがアボートしない。
- `primaryDecides`: シャードがコミットするのはプライマリがコミットしたものだけ。
  クライアントがコミットを聞くのもプライマリがコミットした後だけ。

### txn: 保証しないこと

- **活性**: ロックがいつか解決されることは検査していない。
- **有限の範囲だけ**: シャード 2 つ、キー 3 つ、トランザクション 5 つ(書くもの 4 つ、
  読むだけのもの 1 つ)で、読み書きするキーは固定。`quint run` はランダムな実行
  (既定 3000 本 × 40 ステップ)を見るだけ、`quint verify` は 3 ステップまでの全実行を
  見るだけ。
- 落とした情報: 期限と時計、決定記録の回収(`Collect` の柵)、分割、範囲読み、
  名前空間をまたぐトランザクション(`Mixed`)、ネットワーク上での重複・遅延した
  `Prepare`(調整役の手順としては一度ずつ)。実装との照合(トレースの再生)はまだない。

### txn: 前提が空虚でないこと(到達性のシナリオ、`quint test`)

| シナリオ | 示すこと |
| --- | --- |
| `two::strandedCommitTest` | コミット点の直後で調整役が止まり、別のトランザクションがその書き込みを読んで書いた後、読むだけのトランザクションは片方しか見えないのでコミットしない |
| `two::strandedThenToldTest` | 決定が伝わった後なら、同じ読みは両方を見てコミットする |
| `two::lostUpdateTest` | 読んだ後に書き換えられたトランザクションは準備で拒まれる |
| `two::lockRefusesTest` | 同時に準備すると、先のロックが後を拒む |
| `two::resolvedAfterCommitTest` | コミット点の後に残ったロックは、解決するとコミットになる |
| `two::resolvedBeforeCommitTest` | コミット点の前に残ったロックは、解決するとプライマリでアボートされ、戻った調整役もそれを知る |
| `two::noCommitBeforeEveryPrepareTest` | 全シャードが準備するまでプライマリはコミットしない |

### txn: 感度分析

| 変種 | 壊す規則 |
| --- | --- |
| read-only commits unconfirmed | 読むだけのトランザクションを確認せずにコミットする(PR #36 で直したバグ) |
| prepare ignores changed reads | 準備で「読んだ版の後に書き込みがないか」を見ない |
| prepare ignores locks | 準備で他のロックを見ない |
| resolve ignores the primary | 解決がプライマリの決定によらずアボートする |
| commits before every prepare | 全シャードの準備を待たずにコミットする |

1 つ目の変種は、このモデルのランダムシミュレーションでも数十本で反例が出る。調整役が
どこで止まってもよいので、コミット点の直後で止まる筋も自然に生まれるため。一方、
`crates/sim` の決定論的シミュレーションでは、その筋を障害として明示的に入れるまで
500 シードでも見つからなかった(`crates/sim/tests/isolation.rs` の `Stranded`)。

## `bft/bft.qnt`

### モデル

- 署名は偽造できないので、メッセージは署名者の名前で表す。プロトコルにないものに
  署名できるのは故障レプリカだけ。故障は運営者単位で数える(1 シャード 1 運営者
  1 レプリカ)ので、故障集合はレプリカの集合になる。
- ネットワークはこれまでに送られた全メッセージの集合。どのレプリカも、どれを、
  いつ、どの順で読んでもよく、読まなくてもよい。
- 証明書(`Certificate`・`TimeoutCertificate`)は集合の中の定足数ぶんの票・
  タイムアウト。レプリカはどの証明書もいつ知ってもよい。実装でも故障レプリカが
  `Timeout` の high や `Skip` に入れて転送できるので、実装にない振る舞いは増えない。
- 故障レプリカは任意の票・タイムアウト(本物の証明書付き)を出し、自分が率いる
  ビューで複数のブロックを提案(等価性違反)できる。提案の署名はタイムアウト証明書を
  覆わないので、誰でもブロックを別のタイムアウト証明書と組み替えて転送できる。
- ブロック本体は誰でも取れる(`Fetch` はいつか成功する)とする。安全性の検査なので。
- リーダー表(`schedule::Leaders`)は、実装の `Committee::leader` がメンバー 1〜4 に
  引く表をビュー 1〜16 まで写したもの(`n4f2` だけは攻撃を組むための別の表)。
  トレースの再生が各提案のリーダーを実装と突き合わせるので、表がずれると落ちる。
- クライアントはいつも次のコマンドを持っているとする。そのため、リーダーはビューに
  入った時点で必ず提案する(実装は決めることがあるときだけ提案する)。ビューを途中で
  通過するとき(提案の証明書で入り、続けてタイムアウト証明書で次へ進むなど)も、
  実装どおり途中のビューで提案する。
- モデルが扱うのは 1 エポック。定数 `Changes` のブロックは、委員会が認める委員会の変更
  (`ChangeCertificate`)を持つ(実装の `Core::change_in`)。それを確定したレプリカは
  エポックを終え、その先は確定せず、投票も提案もしない。次の委員会は新しいドメインで
  ビュー 1 から始めるので、メンバーの違う同じモデルになる。`n4f1` では故障した n4 の
  ビュー 2 の 1 つ目のブロック(ブロック 4)が変更を持つ(変更は誰でも転送できる)。

### 保証すること(`safety`、不変条件)

- `agreement`: 正しいレプリカが確定したブロックはすべて一本の鎖に載る。
- `oneBlockPerHeight`: 同じ高さで異なる 2 ブロックが確定しない。
- `voteOnce`: 正しいレプリカは 1 ビューで高々 1 回投票する。
- `noVoteAfterTimeout`: 正しいレプリカは諦めたビューで投票しない。
- `oneCertificatePerView`: 1 ビューで証明されるブロックは高々 1 つ。
- `lockIsCertified`: ロック(知っている最新の証明書)は本物で、ビューはその先にある。
- `proposesOnce`: 正しいリーダーは、クラッシュしても 1 ビューで 1 回しか提案しない
  (2 つ目は故障の証拠になる)。
- `endsAtOneBlock`: エポックを終えた正しいレプリカは、みな同じブロックで終える。
- `nothingAfterTheEnd`: 正しいレプリカは、エポックを終えるブロックより先を確定しない。

### 保証しないこと

- **活性**(いつか確定する)は検査していない。公平性(メッセージがいつか届く、GST 後は
  遅延に上限がある)を仮定した時相性質は書いておらず、モデルはどこで止まってもよい。
  「確定に届きうる」ことはシナリオで示すが、「必ず届く」とは言っていない。
- **有限の範囲だけ**: 4 レプリカ、ビュー 1〜5(`n4f2` は 1〜4)、故障リーダーは 1 ビューで
  2 ブロックまで、リーダー表は固定の 1 通り。`quint run` はその中のランダムな実行
  (既定 3000 本 × 40 ステップ)を見るだけ、`quint verify` は 3 ステップまでの全実行を見る
  だけで、どちらも「どの入力でも成り立つ」証明ではない。決定までに 10 ステップ前後かかる
  ので、3 ステップの有界検査は浅い(4 ステップは 30 分で終わらなかった)。深い攻撃は
  シナリオと感度分析で補っている。
- **有界検査はエポックの終わりを見ない**: 変更の確定には変更のブロックとその後の
  ブロックの証明が要り、3 ステップでは届かない。そこで `quint verify` は変更を除いた
  `n4f1c0` で走らせる(変更を持つ `n4f1` のままだと、`Changes` を展開できず、同じ
  実行を見るのに数倍かかった)。エポックの終わりの不変条件は、シナリオ、ランダム実行、
  終わる実行の探索とその再生で見ている。
- **実装との対応**はトレースの再生(下)で確かめるが、確かめられるのはモデルが
  生んだ実行についてだけ。モデルにない振る舞い(コマンドが尽きたリーダーが提案しない、
  `Forward`、タイマーの長さ)は照合の外にある。
- 落とした情報: バイト列・署名検証・ハッシュ(署名は偽造不能、ブロック ID は衝突しない
  と仮定)、コマンドの中身と「決めることがないときは提案しない」規則、`Fetch`/`Deliver`
  (本体は常に手に入る)、タイマーの長さ、チェックポイント(P4a)と状態同期(P4b)、
  エポックの終わりのチェックポイントの認証と次の委員会への切り替え、変更の署名の検証
  (`Changes` のブロックは認められる変更を持つと仮定)。

### 抽象化が実装より広い(=安全側の)ところ

レプリカはどの証明書・タイムアウト証明書をいつ知ってもよい。自分の票とタイムアウトは
クラッシュで忘れる(実装どおり)が、ネットワークがそれを本人に返してもよい(故障
レプリカの転送で起こりうる。`n4f0` では実装より振る舞いが多い)。故障レプリカは任意の票・タイムアウト・
提案・転送ができる。振る舞いが実装より多いぶんには、安全性の結論は弱まらない。

### 前提が空虚でないこと(到達性のシナリオ、`quint test`)

| シナリオ | 示すこと |
| --- | --- |
| `n4f0::twoChainCommitsTest` | 2 ビュー続けて証明されると最初のブロックだけ確定する |
| `n4f0::timeoutStartsTheNextViewTest` | タイムアウト証明書で次のビューに進み、その提案に投票できる |
| `n4f0::lockRefusesAnOlderBranchTest` | ロックが古い枝への投票を拒む |
| `n4f0::skippedLeaderProposesJustifiedTest` | `Skip` で入ったリーダーは、TC が運ぶ証明書の上に正当な提案を出す(下の「見つかったこと」) |
| `n4f0::crashedLeaderProposesOnceTest` | 提案したリーダーはクラッシュしても同じビューで提案し直さない(同上) |
| `n4f0::noVoteAfterGivingUpTest` | 諦めたビューでは投票しない |
| `n4f1::oneFaultCannotCertifyAForkTest` | 故障 1 台の二重提案はどちらも証明されない |
| `n4f1::crashKeepsTheVoteTest` | クラッシュ後も同じビューで二度投票しない |
| `n4f1::forkAfterTimeoutsTest` | 証明済みの分岐に届き、タイムアウト後の提案が確定する |
| `n4f1::aChangeEndsTheChainTest` | 変更を持つブロックの子孫が証明されて一度に確定するとき、変更のブロックで止まる |
| `n4f1::anEndedReplicaVotesNoMoreTest` | エポックを終えたレプリカは投票せず、率いるビューに入っても提案しない |
| `n4f2::forkDecidedTest` | 故障 2 台(許容量超え)なら `agreement` が破れる |

### 感度分析

`specs/bft/check.sh` は仕様をわざと壊した変種を作り、シナリオのどれかが失敗すること
(検査が破れを見つけること)を毎回確かめる。

| 変種 | 壊す規則 |
| --- | --- |
| no lock rule | 投票時のロック検査(`b.justify >= lock`)を外す |
| votes twice in a view | 1 ビュー 1 票の検査を外す |
| quorum of 2f | 定足数を `n - f` から `n - f - 1` にする |
| one-chain commit | 証明されたブロック自身を確定する |
| crash forgets the vote | 復旧時に投票済みビューを忘れる |
| crash forgets the proposal | 復旧時に提案済みビューを忘れる |
| skip carries no certificate | `Skip` の受け手が TC の運ぶ証明書を学ばない |
| decides past the change | 変更を持つブロックの先まで確定する |
| votes after the end | エポックを終えても投票する |
| proposes after the end | エポックを終えても提案する |

タイムアウト証明書付き提案の high 検査(`b.justify >= tc.high.view`)を外す変種は置かない。
受け手は投票の前に TC が運ぶ証明書を学ぶので、ロック検査が同じブロックを拒み、どの
シナリオでも区別できないため(実装の `Proposal::verify` には多重の防御として残してある)。
同じく、エポックを終えたレプリカが確定を続けない検査(`observe` の `not(ended(s))`)を外す
変種も置かない。終わりの先のブロックを確定するには、その孫の証明書、つまり終わった後に
投じられる票が要るが、ビュー 5 までには、まだエポックにいて票を投じられるレプリカが残らない
ため(実装の `Core::decide` は同じ理由で早く戻る)。

ランダムシミュレーションだけでは、たとえばロック検査を外した変種の反例は 3000 本では
出なかった。そのためシナリオで攻撃の筋を固定して検出している。

### トレースの再生(trace validation)

`crates/bft/src/core/trace.rs` は、モデルの実行(ITF トレース)を 1 ステップずつ実装の
`Core` に再生する。再生側がネットワークと故障レプリカを演じ、モデルの票・タイムアウト・
提案をメンバーの鍵で署名して渡し、コマンドを切らさない。各ステップの後で、正しい
レプリカごとにビュー・最後に投票したビュー・ロック・最後に提案したビュー・入ったときの
タイムアウト証明書・確定したブロックがモデルと同じか、送った提案・票・タイムアウトが
モデルの追加分と同じかを確かめる。

- `cargo test` は `specs/bft/traces/` の固定トレースを再生する。`specs/check.sh` は毎回
  新しいランダムな実行(既定で各インスタンス 100 本 × 40 ステップ)を作って再生する。
- ランダムな実行がエポックを終えることはまれなので、`check.sh` は `not(endedEverywhere)` を
  破る実行(正しいレプリカ全員がエポックを終え、先に終えたものはその後も動く)を探して
  再生する。固定トレースの `n4f1-ended.itf.json` もその 1 本。再生側は `Changes` の
  ブロック(故障リーダーのもの)に、委員会が認める変更を入れる。
- 照合を作る過程で仕様を実装に合わせた点: 即時の提案、実装のリーダー表、クラッシュで
  忘れる票とタイムアウト、自分の提案も検証して不当なら投票しないこと、途中で通過する
  ビューでの提案、自分のタイムアウトも TC に数えること。
- 感度: `Core` をわざと壊した 4 変種(ロック検査を外す、復旧時に提案済みビューを忘れる、
  一連鎖で確定する、タイムアウトで投票済みにしない)は、600 本 × 60 ステップの再生で
  すべて食い違いとして検出された。

### 見つかったこと(直した)

`Skip` で次のビューに入ったリーダーは、タイムアウト証明書の high(署名者が知っていた
最新の証明書のビュー)だけを受け取り、証明書そのものは受け取っていなかった。そのため
自分のロックがそれより古いと、出した提案は全員に `Unjustified` で拒まれ、そのビューは
必ずタイムアウトしていた。今はタイムアウト証明書が最新の証明書そのものを運び
(Jolteon 方式)、受け取ったレプリカはそれを学んでから次のビューに入る
(`skippedLeaderProposesJustifiedTest`)。

さらに、そのリーダーはクラッシュすると同じビューでもう一度、別のブロックを提案していた
(トレースの再生で見つかった)。`Core::recover` が「最後に投票したビュー」を「最後に
提案したビュー」の代わりに使っていて、不当な自分の提案には投票しないので、提案したことが
残らなかったため。分岐は起きないが、正しい運営者が二重提案の証拠を残すことになる。今は
提案したビューもジャーナルの `Safety` に書き、提案を送る前に永続化している
(`crashedLeaderProposesOnceTest`、`proposesOnce` は `safety` に戻した)。

### インスタンス

| モジュール | 構成 |
| --- | --- |
| `n4f1` | 4 台、1 台故障(n4。ビュー 2 と 4 のリーダー) |
| `n4f1c0` | `n4f1` から変更を除いたもの。`quint verify` 用(下記) |
| `n4f0` | 4 台、全員正しい |
| `n4f2` | 4 台、2 台故障。安全性が破れるべき構成 |

## 実行

```sh
npm install -g @informalsystems/quint@0.35.0   # Java 17 以上も(Apalache 用)
specs/check.sh
```

`specs/check.sh` は CI と同じものを走らせる。引数 `run` は Apalache 以外(CI の `quint` ジョブ)、
`verify` は Apalache による有界モデル検査だけ(`quint-verify` ジョブ、約 20 分)、省略すると両方。仕様ごとのディレクトリの
`check.sh`(`bft/check.sh` など)を順に呼ぶだけで、各 `check.sh` は `specs/common.sh` の
回数・評価器・感度分析(`check_mutants`)を使う。新しい仕様はディレクトリと `check.sh` を
足せば加わる。`bft` では型検査、シナリオ(`quint test`)、感度分析、ランダムシミュレーション
(`quint run`)、トレースの再生(Rust のツールチェーンも要る)、Apalache による有界モデル検査
(`quint verify`)を走らせる。回数は環境変数で変えられる(`common.sh` 冒頭を参照)。固定トレースを作り直すには
`specs/bft` で次を走らせる(`n4f0` も同様)。

```sh
quint run --backend typescript --main n4f1 --invariant safety --mbt \
```
