# 仕様と形式検証(Quint)

プロトコルの設計を [Quint](https://quint-lang.org/) で書き、モデル検査で性質を確かめる。
Rust の Kani 証明(`#[cfg(kani)]`)がコード片の全域性と往復を証明するのに対し、ここでは
複数のレプリカと故障を持つプロトコル全体を、メッセージの遅延・順不同・消失・重複と
クラッシュ込みで調べる。

| 仕様 | 対象 |
| --- | --- |
| `bft/bft.qnt` | `crates/bft` の合意(`HotStuff-2` / Jolteon 型の二連鎖コミット、ビューごとのリーダー、タイムアウト証明によるビュー切り替え、クラッシュからの復旧) |

## `bft/bft.qnt`

### モデル

- 署名は偽造できないので、メッセージは署名者の名前で表す。プロトコルにないものに
  署名できるのは故障レプリカだけ。故障は運営者単位で数える(1 シャード 1 運営者
  1 レプリカ)ので、故障集合はレプリカの集合になる。
- ネットワークはこれまでに送られた全メッセージの集合。どのレプリカも、どれを、
  いつ、どの順で読んでもよく、読まなくてもよい。
- 証明書(`Certificate`・`TimeoutCertificate`)は集合の中の定足数ぶんの票・
  タイムアウト。レプリカはどの証明書もいつ知ってもよい。実装でも故障レプリカが
  `Timeout` の high や `Skip` に入れて転送できるので、実装にない振る舞いは増えない。
- 故障レプリカは任意の票・タイムアウト(本物の証明書付き)を出し、自分が率いる
  ビューで複数のブロックを提案(等価性違反)できる。提案の署名はタイムアウト証明書を
  覆わないので、誰でもブロックを別のタイムアウト証明書と組み替えて転送できる。
- ブロック本体は誰でも取れる(`Fetch` はいつか成功する)とする。安全性の検査なので。
- リーダーは実装ではビュー番号のハッシュで選ぶ。モデルはビューごとの固定表で、
  実装が引きうる表の一つとして扱う。

### 保証すること(`safety`、不変条件)

- `agreement`: 正しいレプリカが確定したブロックはすべて一本の鎖に載る。
- `oneBlockPerHeight`: 同じ高さで異なる 2 ブロックが確定しない。
- `voteOnce`: 正しいレプリカは 1 ビューで高々 1 回投票する。
- `noVoteAfterTimeout`: 正しいレプリカは諦めたビューで投票しない。
- `oneCertificatePerView`: 1 ビューで証明されるブロックは高々 1 つ。
- `lockIsCertified`: ロック(知っている最新の証明書)は本物で、ビューはその先にある。
- 正しいリーダーは 1 ビューで 1 回しか提案しない(クラッシュ後も)。

### 保証しないこと

- **活性**(いつか確定する)は検査していない。公平性(メッセージがいつか届く、GST 後は
  遅延に上限がある)を仮定した時相性質は書いておらず、モデルはどこで止まってもよい。
  「確定に届きうる」ことはシナリオで示すが、「必ず届く」とは言っていない。
- **有限の範囲だけ**: 4 レプリカ、ビュー 1〜5(`n4f2` は 1〜4)、故障リーダーは 1 ビューで
  2 ブロックまで、リーダー表は固定の 1 通り。`quint run` はその中のランダムな実行
  (既定 3000 本 × 40 ステップ)を見るだけ、`quint verify` は 6 ステップまでの全実行を見る
  だけで、どちらも「どの入力でも成り立つ」証明ではない。決定までに 10 ステップ前後かかる
  ので、6 ステップの有界検査は浅い。深い攻撃はシナリオと感度分析で補っている。
- **実装との対応**はまだ機械的に確かめていない(手で `core.rs` を読んで写した)。
  ITF トレースを `crates/bft` の sim で再生するモデルベーステストは次の PR。
- 落とした情報: バイト列・署名検証・ハッシュ(署名は偽造不能、ブロック ID は衝突しない
  と仮定)、コマンドの中身と「決めることがないときは提案しない」規則(モデルはいつでも
  提案してよいので、実装より振る舞いが多い)、`Fetch`/`Deliver`(本体は常に手に入る)、
  タイマーの長さ、チェックポイント(P4a)と状態同期(P4b)、委員会の変更。

### 抽象化が実装より広い(=安全側の)ところ

レプリカはどの証明書・タイムアウト証明書をいつ知ってもよい、提案はいつしてもよい、
自分の提案への投票は同じステップ(実装どおり)。故障レプリカは任意の票・タイムアウト・
提案・転送ができる。振る舞いが実装より多いぶんには、安全性の結論は弱まらない。

### 前提が空虚でないこと(到達性のシナリオ、`quint test`)

| シナリオ | 示すこと |
| --- | --- |
| `n4f0::twoChainCommitsTest` | 2 ビュー続けて証明されると最初のブロックだけ確定する |
| `n4f0::timeoutStartsTheNextViewTest` | タイムアウト証明書で次のビューに進み、その提案に投票できる |
| `n4f0::lockRefusesAnOlderBranchTest` | ロックが古い枝への投票を拒む |
| `n4f0::skippedLeaderProposesUnjustifiedTest` | 下の「見つかったこと」 |
| `n4f0::noVoteAfterGivingUpTest` | 諦めたビューでは投票しない |
| `n4f1::oneFaultCannotCertifyAForkTest` | 故障 1 台の二重提案はどちらも証明されない |
| `n4f1::crashKeepsTheVoteTest` | クラッシュ後も同じビューで二度投票しない |
| `n4f1::forkAfterTimeoutsTest` | 証明済みの分岐に届き、タイムアウト後の提案が確定する |
| `n4f2::forkDecidedTest` | 故障 2 台(許容量超え)なら `agreement` が破れる |

### 感度分析

`specs/check.sh` は仕様をわざと壊した変種を作り、シナリオのどれかが失敗すること
(検査が破れを見つけること)を毎回確かめる。

| 変種 | 壊す規則 |
| --- | --- |
| no lock rule | 投票時のロック検査(`b.justify >= lock`)を外す |
| votes twice in a view | 1 ビュー 1 票の検査を外す |
| quorum of 2f | 定足数を `n - f` から `n - f - 1` にする |
| one-chain commit | 証明されたブロック自身を確定する |
| crash forgets the vote | 復旧時に投票済みビューを忘れる |
| timeout certificate ignores high | タイムアウト証明書付き提案の high 検査を外す |

ランダムシミュレーションだけでは、たとえばロック検査を外した変種の反例は 3000 本では
出なかった。そのためシナリオで攻撃の筋を固定して検出している。

### 見つかったこと

`Skip` で次のビューに入ったリーダーは、タイムアウト証明書の high(署名者が知っていた
最新の証明書のビュー)だけを受け取り、その証明書自体は受け取らない。自分のロックが
それより古いと、出した提案は全員に `Unjustified` で拒まれ、そのビューは必ず
タイムアウトする(`skippedLeaderProposesUnjustifiedTest`)。安全性は崩れないが、
メッセージが落ちる状況ではビューが 1 つ無駄になる。Jolteon のようにタイムアウト証明書に
最新の証明書そのものを載せるか、ロックが high より古いリーダーは提案せずに `Fetch`
する、で直せる。

### インスタンス

| モジュール | 構成 |
| --- | --- |
| `n4f1` | 4 台、1 台故障(2 番目と 5 番目のビューのリーダー) |
| `n4f0` | 4 台、全員正しい |
| `n4f2` | 4 台、2 台故障。安全性が破れるべき構成 |

## 実行

```sh
npm install -g @informalsystems/quint@0.35.0   # Java 17 以上も(Apalache 用)
specs/check.sh
```

`specs/check.sh` は CI(`quint` ジョブ)と同じものを走らせる: 型検査、シナリオ
(`quint test`)、感度分析、ランダムシミュレーション(`quint run`)、Apalache による
有界モデル検査(`quint verify`)。回数は環境変数で変えられる
(スクリプト冒頭を参照)。
